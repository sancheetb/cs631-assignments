EXTENDED INSERT BENCHMARK — B+ tree vs LSM tree
================================================
Environment: PostgreSQL 18.6 + custom lsm AM.  The data is loaded from
sample_data.csv (500,000 rows); one B+ tree index and one LSM index are built;
then FOUR rounds of 150,000 random-key inserts are run (600,000 new rows,
1,100,000 total).  shared_buffers=4MB so the ~11MB B+ tree index is cold.
The lsm3merge background worker is paused only during each timed insert and
resumed between rounds to drain T_merging into T_base.

These are the numbers produced by the full ./run_demo.sh (Step 3):

  Round   B+ tree (ms)   LSM (ms)   LSM speedup
  -----   ------------   --------   -----------
    1          923.6       1100.6      0.84x   (first flush warm-up)
    2         2076.1       1172.6      1.77x
    3         2592.7       1051.8      2.47x
    4         3170.3       1015.9      3.12x

(See README.md and an earlier standalone run for a variant where round 1
is already even; the first-round variance is the initial MemTable swap and
cold catalog/buffer warm-up.  The widening trend is the point: B+ tree insert
cost grows ~3.4x while LSM stays flat.)

Why: the B+ tree index exceeds shared_buffers, so random inserts cause disk
I/O and page splits and it degrades as it grows.  The LSM always writes to
the small memory-resident T_active; the expensive merge into T_base is done
asynchronously by the worker between rounds, so writer latency stays flat.

LSM level progression across the rounds:
  after R1: swaps=1, extracted=150000
  after R2: swaps=2, extracted=300000
  after R3: swaps=3, extracted=450000
  after R4: swaps=4, extracted=600000

Correctness: both tables ended at 1,100,000 rows; sample-key comparison
mismatched = 0; lsm3merge worker alive throughout.

How to reproduce:  ./run_demo.sh   (all three steps, including this test)
              or:  ./psql.sh -f benchmark_inserts.sql  (this test alone)
